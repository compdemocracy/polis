This is a static source inventory, not a declaration that every script runs in deployment. Python/TypeScript syntax trees identify direct lookups; Rust literal lookups, local wrappers, finite loops, known environment-map aliases, and embedded child scripts are resolved separately. Reads in tests, certification tools, and Cargo build scripts are included and labeled. Comments, assignment-only writes, vendored dependencies, and dependency-internal environment lookups are not named application reads. A shared helper can accept names supplied by future/external callers; inherited subprocess and SDK environments are open-ended. See the explicit boundaries below.

Defaults describe the lookup expression at that site. `None`/`undefined` is absence, not a guarantee that downstream code accepts absence. Ordered fallbacks, constructor overrides, config-map expressions, and validation can change effective behavior. Secret or environment-specific identifier defaults are deliberately not reproduced; their source locations are retained. “No” means not intrinsically a credential, not suitable for public disclosure. A read does not establish that the value controls an active feature.

## Other boundaries

- The Rust bridge forwards only six caller keys after `env_clear`; it also writes fixed numerical settings and the publisher connection separately. The forwarded names are counted above; generated assignments are not caller reads. See [coordinator-rs/src/bridge.rs:292](../coordinator-rs/src/bridge.rs#L292).
- Python certification helpers copy arbitrary caller environments and may overwrite numerical/thread/database keys before child launch. See [coordinator-rs/ci/run.py:94](../coordinator-rs/ci/run.py#L94) and [coordinator-rs/ci/replay_pins.py:67](../coordinator-rs/ci/replay_pins.py#L67). Copied values can be consumed by runtimes or third-party libraries outside this census.
- Cargo `env!`/`option_env!` and `build.rs` inputs are build-time values, not deployed-service runtime settings. See [coordinator-rs/build.rs:1](../coordinator-rs/build.rs#L1).
- CDK shell review distinguishes local variables (`BOOTSTRAP_PHASE`, `BOOTSTRAP_DOWNLOAD_DIR`, `COMPOSE_VERSION`, `COMPOSE_SHA256`, `IMDS_TOKEN`, `POLIS_REF`) from inherited environment inputs: those variables are assigned in the emitted script. TypeScript `${...}` interpolation is not a shell environment read. See [cdk/ciEc2.ts:480](../cdk/ciEc2.ts#L480). The embedded import-worker Node read and test shell inputs are counted above.
- Shell `OLLAMA_*` defaults are counted at their first expansions; later `$MODEL`, color constants and shell `PIPESTATUS` are local/shell state, not additional deployment inputs. The other three scoped `.sh` scripts and extensionless `delphi` launcher contain no literal caller environment lookups. Dockerfile and Make expansions are counted separately above; Make `ZID`/`RID` can come from a caller environment or command line. The two notebooks have no environment reads in code cells; three Delphi Clojure tests have none, while the coordinator Clojure diagnostic has two. See [delphi/scripts/setup_ollama.sh:11](../delphi/scripts/setup_ollama.sh#L11).
- `GOOGLE_APPLICATION_CREDENTIALS` is written by server configuration, then consumed by the Google library; it is not a direct server-source read. See [server/src/config.ts:228](../server/src/config.ts#L228). `AWS_SESSION_TOKEN` likewise belongs to an SDK credential chain, with the explicit-pair limitation described in [server/src/utils/dynamoClient.ts:52](../server/src/utils/dynamoClient.ts#L52).
- Root Compose interpolation, frontend `import.meta.env`, the main Clojure service and `server/index.ts` lie outside the four requested read scopes. Their relevant deployment and P065 service entries are retained separately in [deployment configuration](deployment-configuration.md).
